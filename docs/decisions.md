| 2026-09-25 | Supersedes the entry above: test-split flaw-label reconstruction from VizWiz_quality_issues_train_val_test.csv is rejected | scripts/validate_reconstruction.py reconstructs per-flaw vote counts from the CSV's raw per-worker rows and compares them against the published train.json/val.json vote counts. Three implementation defects were identified and fixed: a UTF-8 BOM on the CSV's first header breaking the IMG column key; a combined filename causing filename-based split inference to misassign every row to "train"; and a 12-digit vs 8-digit image-ID zero-padding mismatch between the CSV and the JSON files. With all three fixed, exact-match rate is 331-365/23,431 (1.4-1.6%) on train and 0/7,750 (0%) on val. Root cause, confirmed via https://vizwiz.org/tasks-and-datasets/vqa/: the CSV is annotation data from the deprecated pre-2020 VizWiz release (12-digit zero-padded filenames, e.g. VizWiz_val_000000028000.jpg; 20,000 train / 3,173 val), while train.json/val.json/test.json come from the current release (8-digit filenames, e.g. VizWiz_val_00028000.jpg; 20,523 / 4,319). The two releases use different, unrelated image numbering with no published crosswalk. The 331-365 apparent matches are therefore coincidental collisions between two independent numbering schemes, not genuine reconstructions, and cannot be distinguished from true matches after the fact - none may be used. Crosswalk recovery (e.g. matching deprecated-to-current images by content) is not pursued: no mapping is published, and the val-split-in-half fallback is the primary evaluation plan independent of this result. Consequence: test-split labels, for both flaws and recognisability, are unavailable; the val-split-in-half fallback (fixed seed 42) applies to all heads, not recognisability alone |

| 2026-10-03 | The 256px padded image cache is CNN input only; classical features are computed from the original images, aspect ratio preserved, no padding, at two fixed long-edge resolutions: 224px and 512px | CNN backbones take ~224px input, so the 256px cache loses nothing the network uses. Classical descriptors are different: downsampling acts as a low-pass filter that makes mildly blurred and sharp images indistinguishable to Laplacian variance and Tenengrad; black letterbox padding lowers luminance mean and inflates dark-pixel fraction by an amount set by aspect ratio rather than exposure; and border edge energy would measure the photo/padding boundary rather than the photo's own edge. Computing classical features from the cache would handicap Arm 1 on exactly the photometric flaws (BLR/DRK/BRT) the central hypothesis predicts it handles well, biasing the comparison. A fixed resolution per extraction is required because blur metrics are scale-dependent; images whose native long edge is below the target are upsampled to keep the scale fixed, with native dimensions recorded per row so their count and effect can be checked. Two resolutions, same code path and same features: classical@224 is the primary comparison configuration, matching the CNN's 224px input so that method is the only variable across classical vs CNN vs hybrid (the hybrid uses the 224 features); extracting at 512 only would make a classical win on BLR inseparable from classical having been given more pixels. classical@512 is reported as a separate labelled row, the practical-deployment configuration: a real application has the full-resolution photo and classical features are cheap to compute on it, while the CNN is capped at its input size. Interpretation rule, fixed before any results exist: 224 and 512 close on BLR means resolution is not the driver; 512 clearly better on BLR means blur detection needs high-frequency content that 224px removes, reported as a finding and as a limitation of CNN-based quality assessment at standard input sizes; weak at both means suspect the implementation and debug before concluding. 512 remains provisional on Stage B's resolution measurements: lowered rather than widely upsampled if a meaningful share of originals fall below it |
| 2026-10-03 | CNN training augmentation excludes aggressive random crops (e.g. RandomResizedCrop) | Cropping changes what is in frame, which is the FRM target label; an image labelled well-framed can become cut off after a crop, producing label noise on the most prevalent flaw |
| 2026-10-03 | No EXIF auto-rotation anywhere in the image pipeline (removed ImageOps.exif_transpose from scripts/prepare_cache.py) | ROT is a target label, so the pipeline must present images in the orientation annotators judged. No official source (task page, paper, baseline README) states an EXIF policy, but the evidence points to raw orientation: the paper defines ROT as "does the image need to be rotated for proper viewing?" with annotators rotating images themselves via an interface toolbar, and the official baseline loads images with Keras image.load_img, which opens files with PIL and does not apply EXIF orientation. Annotation predates browsers applying EXIF orientation by default (Chrome 81 / Firefox 77, 2020). Auto-rotating would risk presenting upright pixels carrying ROT-positive labels. Also makes the cache consistent with src/data/dataset.py, which never auto-rotated. Loaders can apply EXIF orientation silently: OpenCV's cv2.imread does so by default (unless passed cv2.IMREAD_IGNORE_ORIENTATION), whereas PIL Image.open does not. All image reads in this project therefore go through PIL, including the classical feature extractor (src/features/classical.py), so the cache, the dataset and the classical features see identical orientation; OpenCV is used only on already-decoded arrays. Measured (scripts/check_exif_rotation.py, reports/exif_rotation_check.md): not a no-op. Every annotated train image carries an Orientation tag; 21,483 (91.7%) are 1 (normal) and 1,948 (8.3%) are 6 (rotated 90 CW), so auto-rotation would change the pixels of 1,948 images. The ROT>=2 rate is 53.4% for Orientation 6 against 13.7% for Orientation 1 (about 3.9x), confirming that annotators saw raw, uncorrected orientation. Auto-rotating would have presented 1,040 of the 3,986 ROT-positive train images (26.1%) upright while labelled as needing rotation |
| 2026-10-03 | Images are letterbox-padded to a square, not stretched, unlike the official baseline | The official baseline (chiutaiyin/VizWiz-QualityIssues README) resizes with Keras load_img(target_size=(448,448)), which ignores aspect ratio and stretches. Stretching distorts geometry, and framing (FRM) is a target label, so this project pads instead. A deliberate divergence from the reference implementation, to be stated in the report |
| 2026-10-03 | ROT is treated as partly a display-pipeline artifact: it labels raw stored orientation, which modern viewers correct for EXIF-tagged images. Models are trained and evaluated against the label as annotated | 1,040 of the 3,986 ROT-positive train images (26.1%) are EXIF Orientation 6 images that annotators saw sideways because the annotation interface displayed raw pixels; current phones, browsers and apps apply the tag and show these images upright. ROT therefore combines two causes: the camera genuinely held at the wrong angle (present among Orientation 1 images, 13.7% ROT>=2) and software ignoring the orientation tag. Training and evaluation follow the label as annotated, consistent with the no-auto-rotation decision; the combination is reported as a finding and a limitation. For the demonstration application (Stage H), uploads usually arrive already EXIF-corrected, so the orientation convention at inference must be set explicitly rather than inherited from the upload component |
| 2026-10-04 | classical@512 is kept only if at most 10% of train+val originals have a native long edge below 512px; otherwise the second resolution is lowered to the largest multiple of 32 that at least 90% of originals reach natively. classical@224 is subject to the same check | Classical features resize every image to a fixed long edge because blur metrics are scale-dependent. An original below the target must be upsampled, and interpolation smooths it, lowering Laplacian variance and Tenengrad so the image measures blurrier than it is - an artifact of preprocessing, not a property of the photo. A small upsampled share adds limited noise; a large one would make classical@512 partly a measurement of upsampling, invalidating the pre-registered 224-vs-512 interpretation rule (entry 2026-10-03). The 10% cut-off is a judgement call fixed before native resolutions were measured, so that the outcome cannot steer it. Measured in Stage B from image headers read directly from the original zip archives (src/eda/image_props.py, scripts/extract_image_properties.py) |
| 2026-10-04 | classical@512 confirmed under the upsampling rule; Stage C additionally reports BLR at 512 on the natively-below-512 subset | Measured on 27,306 train+val originals (reports/eda.md): 9.3% have a native long edge below 512px (limit 10%), 0.3% below 224px, median 1296px. The rule is met, so 512 stays. The margin is small, so the upsampled subset is evaluated separately to show directly whether interpolation distorts the sharpness features rather than assuming it does not |
| 2026-10-04 | Every ROT result is reported against a shape-only reference (AP 0.258), and Stage F reports CNN ROT AP separately for EXIF orientation 1 and 6 | Raw pixel shape encodes the EXIF orientation tag almost perfectly (all 2,186 orientation-6 images are landscape-shaped vs 144 of 25,120 orientation-1 images), and landscape shape alone predicts ROT>=2 with AP 0.258 against a 0.170 base rate on train. Within orientation 1, shape carries no signal (AP 0.137 at a 0.137 base rate). The letterbox-padded CNN input preserves shape, so a CNN can approach AP 0.26 on ROT without using content. A ROT score is therefore only evidence of content understanding when it clearly exceeds the shape-only reference, and orientation-1 performance isolates it. Preprocessing is not changed: the ROT label refers to raw orientation (entry 2026-10-03) |
| 2026-10-04 | Error analysis reports per-flaw performance on images carrying that flaw alone, in addition to all images | Flaws co-occur with blur on train at >=2 votes: P(BLR given BRT) 64%, P(BLR given OBS) 64%, P(BLR given DRK) 50% (lift 1.2-1.6). A model can score on a photometric flaw partly through blur cues, so the hypothesis test (classical competitive on BLR/DRK/BRT) needs single-flaw results to show that a classical score on DRK or BRT measures exposure rather than co-occurring blur |
