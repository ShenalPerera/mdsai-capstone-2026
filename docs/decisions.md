| 2026-09-25 | Train image loader must filter to the 23,431 IDs in train.json, not glob the images/train folder | The raw train.zip image pool contains 523 extra files beyond the 23,431 annotated images (VizWiz_train_00023431.jpg-00023953.jpg, a contiguous block immediately after the last annotated ID), confirmed via a full disk-vs-annotation diff with zero missing annotated files. These extra images are privacy-redacted (see entry below) and carry no quality-issue labels, so they must be excluded from training |
| 2026-09-25 | Test-split flaw labels are recoverable; recognisability is not | VizWiz_quality_issues_train_val_test.csv holds raw per-worker votes (IMG, WORKERID, per-flaw 0/1, REJECT, SPLIT) for all three splits, so per-flaw vote counts for test can be reconstructed by grouping on IMG and summing non-rejected rows - but the CSV has no unrecognizable column, so the recognisability head still has no test labels and needs the val-split-in-half fallback |
| 2026-09-25 | Supersedes the entry above: test-split flaw-label reconstruction from VizWiz_quality_issues_train_val_test.csv is rejected | scripts/validate_reconstruction.py reconstructs per-flaw vote counts from the CSV's raw per-worker rows and compares them against the published train.json/val.json vote counts. Three implementation defects were identified and fixed: a UTF-8 BOM on the CSV's first header breaking the IMG column key; a combined filename causing filename-based split inference to misassign every row to "train"; and a 12-digit vs 8-digit image-ID zero-padding mismatch between the CSV and the JSON files. With all three fixed, exact-match rate is 331-365/23,431 (1.4-1.6%) on train and 0/7,750 (0%) on val. Root cause, confirmed via https://vizwiz.org/tasks-and-datasets/vqa/: the CSV is annotation data from the deprecated pre-2020 VizWiz release (12-digit zero-padded filenames, e.g. VizWiz_val_000000028000.jpg; 20,000 train / 3,173 val), while train.json/val.json/test.json come from the current release (8-digit filenames, e.g. VizWiz_val_00028000.jpg; 20,523 / 4,319). The two releases use different, unrelated image numbering with no published crosswalk. The 331-365 apparent matches are therefore coincidental collisions between two independent numbering schemes, not genuine reconstructions, and cannot be distinguished from true matches after the fact - none may be used. Crosswalk recovery (e.g. matching deprecated-to-current images by content) is not pursued: no mapping is published, and the val-split-in-half fallback is the primary evaluation plan independent of this result. Consequence: test-split labels, for both flaws and recognisability, are unavailable; the val-split-in-half fallback (fixed seed 42) applies to all heads, not recognisability alone |
| 2026-09-25 | Root cause of the 523 extra train images confirmed: privacy redaction, not stray data | Per https://vizwiz.org/tasks-and-datasets/vqa/: "VizWiz_train_00023431.jpg - VizWiz_train_00023958.jpg are images which include private information that is obfuscated using the ImageNet mean." This matches the extra block identified in the entry above. The documented range spans 528 images (23431-23958 inclusive); the disk-vs-annotation diff found 523 extra files (23431-23953), 5 fewer than documented - a discrepancy not investigated further since it does not affect the exclusion decision. The full redacted range (23431-23958) lies entirely outside the annotated range (0-23430), so no training image used by this project contains redaction artifacts |
| 2026-09-25 | Project titled by problem domain, not dataset - VizWiz is one realisation of the problem, not the subject | Naming the dataset would wrongly narrow the contribution. New title: "Actionable Image Quality Assessment for Assistive Photography", subtitle "A comparative study of classical, deep, and hybrid approaches". Also switched to "blind and low-vision (BLV) users" (standard accessibility terminology) throughout, keeping "VizWiz" named only under the Dataset section |
